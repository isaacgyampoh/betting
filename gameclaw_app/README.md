# GameClaw mobile

A Flutter application. Not a wrapper: the UI is rendered by Flutter and the app loads no website.

## Requirements

- Flutter **3.47.7** or newer (3.35 cannot resolve `drift_dev`)
- JDK **21**. Gradle 8.12 rejects Java 25, which is what Flutter picks up by default on this
  machine, so point it at 21 once: `flutter config --jdk-dir=$(/usr/libexec/java_home -v 21)`
- Android SDK with platform 35+

## Running

```bash
flutter pub get
flutter analyze
flutter test
flutter build apk --debug
```

`lib/data/local/cache.g.dart` is generated by drift and committed, so a fresh checkout builds
without a codegen step. Regenerate it after changing the table:

```bash
dart run build_runner build --delete-conflicting-outputs
```

### Against a local server

A debug build may talk to a development server on this machine. `adb reverse` points the phone's
`localhost` at it; the cleartext exception for that lives in `src/debug` and is absent from a
release build, which keeps Android's refusal of plain HTTP:

```bash
adb reverse tcp:3000 tcp:3000
flutter build apk --debug \
  --dart-define=GC_API_BASE=http://localhost:3000/api/v1 \
  --dart-define=GC_AUTH_BASE=http://localhost:3000/api/v1 \
  --dart-define=GC_GOOGLE_SERVER_CLIENT_ID=<web client id>
```

## Signing in

Google, against GameClaw's own API. The app gets an ID token from Google natively, posts it to
`GC_AUTH_BASE`, and GameClaw verifies it against Google's JWKS and issues its own session. There is
no email-and-password form and no Supabase in the path.

Two flags decide this, and **a release build needs both**:

| Flag | What it does |
| --- | --- |
| `GC_AUTH_BASE` | GameClaw's auth endpoints, e.g. `https://gameclaw-api.onrender.com/api/v1`. **When set, Supabase is not involved at all.** |
| `GC_GOOGLE_SERVER_CLIENT_ID` | The **Web** OAuth client id - not the Android one. See below. |

Leave `GC_AUTH_BASE` empty and the build falls back to the Supabase path (`GC_SUPABASE_URL` and
`GC_SUPABASE_ANON_KEY`), which is the rollback and nothing else. It is one flag to go back to, and
one flag to ship by mistake: a release built without `GC_AUTH_BASE` signs in against a backend that
is being retired. Check a built APK if in doubt -

```bash
# Release keeps Dart in libapp.so; a debug build keeps it in kernel_blob.bin, so match both.
unzip -p app-release.apk 'lib/*/libapp.so' 'assets/flutter_assets/kernel_blob.bin' 2>/dev/null \
  | grep -ac 'supabase\.co'
```

A release on the right path prints `0`: no Supabase hostname is compiled into it. Grep the binary
directly rather than piping through `strings` - macOS `strings` breaks the hostname across lines
and the match silently never fires.

### The Web client id, not the Android one

This is the counter-intuitive part of native Google sign-in and the usual reason it fails. The
Android client is what lets Google trust the app - matched by package name and signing fingerprint,
never named in code. The Web client is what the ID token is *addressed to*, and that audience is
what the server checks, so the Web id is the one the app hands over. Supplying the Android id
produces a token the server rejects.

The session lives in the OS keystore and is refreshed on the first request that needs it, one
refresh at a time - refresh tokens rotate, so six screens loading at once would otherwise fire six
refreshes and five would be rejected with a token that no longer exists.

Signing out clears the cache as well as the session. A phone gets handed around.

## The backend

The app needs an API for everything it shows. It holds a user's session token and nothing else:
the football provider key, the bookmaker credentials and the database all stay server-side, where
a decompiled APK cannot reach them.

The host is a build flag, never hard-coded:

```bash
flutter build apk --debug --dart-define=GC_API_BASE=https://<host>/api/v1
```

Without the flag it points at `http://10.0.2.2:3000/api/v1`, which is how an Android emulator
reaches a server running on the host machine.

The production host is `https://gameclaw-api.onrender.com/api/v1`, a Render web service in
Frankfurt with its own Postgres. `gameclaw.win` and `www.gameclaw.win` stay as they are - they are
the marketing site and serve no API.

## Layout

```
lib/
  app/              navigation shell and router
  data/             API client, failures, repositories, local cache, session
  domain/           models - the app's own view of football
  features/         one directory per tab, plus auth and the match centre
  theme/tokens.dart the design system's primitives
  ui/components/    the design system's widgets
```

## The design system

One place decides what things look like. `theme/tokens.dart` holds the colours, the 4pt spacing
scale, the radii, the fixed component heights, the motion durations and the type scale;
`ui/components/` holds the widgets built from them. Nothing outside those two directories
hard-codes a colour, a gap or a duration.

The direction is a dark, dense, information-first product read on a phone, often outdoors and
often one-handed. That drives the rest: near-black surfaces so a bright field never washes out a
score; one electric-lime accent spent only on what is live or actionable, so that when it appears
it means something; hairlines instead of cards, because thirty fixtures do not need thirty boxes
around them; and tabular figures everywhere a number appears, because a column of scores that does
not line up is a column nobody scans.

Tabs appear only when there is something behind them. A Statistics tab that is always empty is
worse than no tab: it promises data the provider does not give us, every single time.

## Two rules the code enforces

**Missing is not zero.** A competition that publishes no score and a match that genuinely finished
0-0 are different facts. Anything a provider may not supply is nullable, and a screen must handle
null as "not published" rather than as a number. `Coverage` travels with the data so an empty list
can be told apart from a competition that never publishes one.

**Nothing is invented.** No screen shows a fixture, score, statistic, price or booking code that
did not come from the server. A screen with no data yet says so, and says which kind of nothing it
is: a competition that publishes no timeline, a plan that did not return one, a provider that was
briefly busy and a match that has not kicked off are four different sentences.

## The cache, and what it is not for

Responses are kept on disk so a bad connection still shows what was last seen, with the time it was
read on screen. Only a connection failure or a timeout reaches for it. Anything the server actually
answered - unauthorised, not found, rate limited - is passed through, because showing yesterday's
list to someone whose session expired hides the one thing they need to fix. Same rule in
`lib/data/retry.dart`: a transport problem may be worth another go, a decision is not.
